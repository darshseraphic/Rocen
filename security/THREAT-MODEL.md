# Rocen Security Audit — Part 2 of N: Section 2, Threat Model (Attackers A–G)

Continues directly from Part 1 (Cryptography Audit). Section 1 (security model) already covered in the original pass. This part covers Section 2 in full.

## Attacker A — Ordinary malicious app (non-root)

**Assumption:** a different, non-privileged Android app installed on the same device, with no special permissions beyond what any app can request/hold.

### What this attacker can and cannot reach

| Surface | Reachable by Attacker A? | Evidence |
|---|---|---|
| Flutter `MethodChannel`s (`screen_security`, `device_integrity`, `secure_keystore`) | **No.** | `MethodChannel` is bound to a specific `FlutterEngine.binaryMessenger` instance inside Rocen's own process — it is not an Android IPC/Binder-exposed interface reachable from another app's process, regardless of the channel's string name looking like a reverse-DNS identifier. This needed to be checked and stated explicitly because the naming convention can look alarming out of context; it is not a real exposure. |
| Exported `MainActivity` | **Yes, but only to launch the app.** | `android:exported="true"` (`AndroidManifest.xml` line 20) is required for the `LAUNCHER`/`MAIN` intent-filter to work on Android 12+ and is standard for every launchable app. Another app can start `MainActivity`, but cannot pass it arbitrary data beyond a normal launch `Intent` — no custom intent extras are read by `MainActivity.kt` in the reviewed code (no `intent.getStringExtra(...)` or similar was found), so there is no attacker-controlled-input surface here beyond "can cause the app to open," which is available to any app for any other app on stock Android regardless. |
| Exported `super_native_extensions.DataProvider` (`super_clipboard`'s content provider) | **Not confirmed either way — flagged for follow-up.** | `android:exported="true"` with `android:grantUriPermissions="true"` and no `android:permission` attribute (`AndroidManifest.xml` lines 39-43) means the provider is queryable by any app that constructs the right content URI, *unless* `super_native_extensions`'s own native code internally checks caller identity or requires a specific, unguessable, per-operation URI (a common and legitimate pattern for clipboard-transfer providers, where the URI itself functions as a one-time capability token). **I do not have this plugin's native source**, so I cannot confirm which of these is actually true. This is filed as: *"Not confirmed; requires additional evidence — specifically the native Android source of `super_native_extensions`'s `DataProvider` class — because the manifest declaration alone permits either a safe capability-URI pattern or an unsafe open-query pattern, and only the implementation distinguishes them."* |
| System clipboard (via Rocen's own COPY feature) | **Yes, by clipboard's inherent nature.** | Rocen's Clipboard media viewer implements a genuine COPY-to-system-clipboard feature (built this session, via `super_clipboard`). Once an image is copied, **any other app that reads the system clipboard can see it** — this is not a Rocen bug, it is the correct and expected behavior of "copy to clipboard" as a feature; the user explicitly requested this action. Relevant note: on Android 10 and below, any app could poll the clipboard silently in the background; Android 12+ shows a system toast whenever an app reads clipboard content, meaningfully reducing (but not eliminating) silent clipboard-sniffing. This is a platform-level mitigation Rocen benefits from passively, not something it implements itself. |
| Screenshots / recent-apps thumbnail / screen recording of Rocen's own screens | **Yes, for every screen except the Settings tab specifically.** | **Confirmed, precise finding:** `_setScreenshotProtection(true)` (`FLAG_SECURE`) is called only in `_SettingsScreenState.initState()` and explicitly turned back **off** in `_SettingsScreenState.dispose()` (`settings.dart` lines 61-71). This means `FLAG_SECURE` protection is active *only* while the user is physically on the Settings screen, and is torn down the instant they navigate to any other tab. QuickNote (where plaintext or decrypted note content is displayed), Clipboard (personal photos/videos), Bookmarks, and IdeaInbox all run with **no screenshot/recording protection at all**, and — more subtly — even *within* Settings, screenshot protection has no finer granularity: it's on for the entire Settings screen (e.g., while browsing generic app-color-theme options) and off everywhere else, rather than being scoped specifically to the moments that actually display secrets (password entry fields, the recovery-phrase reveal dialog, the GitHub token field). A malicious app with the (fairly common, often auto-granted or easily-approved) screen-recording/screenshot-adjacent permission, or simply a user's own **screen-recording software** running for an unrelated reason, or Android's own "recent apps" task-switcher thumbnail (captured automatically by the OS for *every* app unless `FLAG_SECURE` is active at the moment of backgrounding) can capture the QuickNote editor with an unlocked note's plaintext visible, or the Clipboard viewer's media, at any time. |
| Intents / share sheets | **Bounded to what the user explicitly shares.** | The `<queries><intent android:name="PROCESS_TEXT">` declaration and `SharePlus`-based sharing (confirmed via the `share_plus` dependency used in `clipboard.dart`/`quicknote.dart`) both operate on explicit user action (tapping SHARE) — no code path was found that shares data to another app without a direct user tap triggering it. |

**Severity of the confirmed finding (screenshot protection scope): ORANGE.** Not a network/crypto break, but a genuine, demonstrable gap between the apparent intent of the feature (protect sensitive on-screen content from capture) and its actual, narrow implementation (protects only the Settings screen, and un-selectively covers all of it rather than the actually-sensitive moments).

## Attacker B — Filesystem/app-data extraction (no root required for this scenario — e.g., unencrypted device backup, or physical access to an unlocked device with USB debugging enabled)

**What this attacker receives, and what it's sufficient to recover, itemized exactly as the spec requests:**

| Item | Recoverable from a raw filesystem/Hive-box extraction? | Why |
|---|---|---|
| Unencrypted notes (`type: 'note'`) | **Yes, fully, immediately.** | `rocen_captures_box` is an unencrypted Hive box (confirmed, no `encryptionCipher` anywhere) storing `CaptureItem.content` in plaintext for this type. No further attack needed. |
| Note titles (even of *encrypted* notes) | **Yes, fully, immediately.** | `CaptureItem.title` is stored unencrypted regardless of `type` (confirmed via `database.dart`'s `toMap()`/`fromMap()`, which apply no encryption to the `title` field under any condition). |
| Encrypted note content (`type: 'encrypted_note'`) | **Yes — see the critical caveat below.** | The ciphertext itself is extracted, but per **Finding 3A from Part 1**, `system_crypto_pin` (also extracted from the same unencrypted box) can be fed **directly** into the shipped `CryptoEngine.decryptProcess` function to recover the plaintext, with **no password-cracking step required at all.** This is the single most consequential finding for this specific attacker: Attacker B does not need to be Attacker C (rooted/compromised device with live memory access) to fully defeat Rocen's note encryption — a cold filesystem copy is sufficient, because the "key" needed is sitting right next to the ciphertext in the same unencrypted box. |
| Passwords (raw) | **No — this specific value is not recoverable directly.** | The raw password is never stored anywhere in the reviewed code; only its Argon2id derivative (`system_crypto_pin`) is. |
| Password hash/verifier | **Yes, fully.** | `system_crypto_pin` extracted directly, unencrypted. |
| Encryption keys | **Effectively yes, per the 3A finding — not because the "key" is stored directly, but because the value that is stored (`system_crypto_pin`) is directly usable as one.** | Restated for this section's specific framing per the spec's checklist. |
| GitHub tokens | **Conditionally — depends on hardware-wrap success.** | `github_access_encrypted` is stored as: (a) if `hardwareWrap` succeeded when saved, an Android-Keystore-wrapped blob — **not** directly decryptable from a cold filesystem copy alone, since the wrapping key lives in Keystore/StrongBox/TEE, which a pure filesystem extraction (without also compromising the OS's key storage, i.e., without also being Attacker C) cannot read; or (b) if `hardwareWrap` failed (device lacks the capability, or the call errored), the value falls back to the software-only `CryptoEngine.encryptProcess(payload, pinHash)` ciphertext — which, per the same 3A finding, **is** directly decryptable using the co-located `system_crypto_pin` value, with no hardware boundary protecting it at all in that fallback case. **This means the GitHub token's actual protection level for this attacker is conditional on whether hardware-wrapping succeeded at save time** — a meaningful, device-dependent inconsistency worth the user/developer knowing about explicitly, since there is no UI indicator anywhere in the reviewed code that tells the user which protection tier their specific token is actually under. |
| Recovery material (mnemonic) | **No.** | Confirmed in Part 1 (Section 3G) — never persisted anywhere. |
| Device key wrap data (`device_key.json`-equivalent local state) | The local device only stores `known_password_generation`/`known_password_change_id` (non-sensitive integers/strings) and, if pending, `password_state_pending_generation`/`_pending_change_id`/`_pending_reason` — none of these are secrets on their own. The actual wrapped-secret material (`wrapSalt`, `wrapNonce`, `wrappedAuthSalt`) lives only in `device_key.json` **on GitHub**, not locally — so a local-only extraction does not directly yield this, though see Attacker D for what happens if GitHub access is also compromised. |

**Overall severity for Attacker B: RED**, driven entirely by the 3A finding — this attacker profile (no root, no live memory access, just a copy of app data) achieves full compromise of encrypted note confidentiality, which is a materially worse outcome than a "properly separated" architecture would allow for this same attacker (who should, in a correctly-built system, still need to brute-force the actual password to get anywhere).

## Attacker C — Rooted/compromised device (live memory + privileged OS access)

**What Rocen can realistically still protect against this attacker, stated honestly rather than optimistically:**

- **Nothing that depends on Android Keystore/StrongBox/TEE's *isolation from the OS* is meaningfully protected**, by definition — a genuinely root-compromised device means the attacker can, at minimum, request the same Keystore operations the app itself can request (since `KeyStore.getInstance("AndroidKeyStore")` operations are gated by which *app/UID* asks, and a rooted device gives an attacker the ability to run code *as* that UID, or to directly instrument the app's own process). **StrongBox** (a genuinely separate secure element chip, where present) is the one component that meaningfully resists even this — StrongBox-backed keys cannot have their raw key material extracted even by root, since the key never leaves the secure element's own hardware boundary; only the *ability to invoke* the key (encrypt/decrypt using it) is exposed to the OS/app layer. `getOrCreateHwKey` (`MainActivity.kt`) does attempt StrongBox first (`generateHwKey(alias, strongBox: true)`), falling back to TEE-only on `StrongBoxUnavailableException` — this is the correct approach, and on a device that actually has StrongBox hardware and where the key generation succeeded at that tier, root access alone does not directly yield the raw AES key, only the *ability to invoke* it (which is still a meaningful capability for an attacker actively running code on the device, but is a different, narrower capability than raw key extraction).
- **RAM-locking (`mlock`) does not meaningfully help against this attacker either** — as documented in the prior report's Finding C-4 with direct evidence from this session's own test logs, `mlock` frequently fails outright on the tested configuration, and even where it succeeds, a root-privileged attacker with live memory-inspection tooling (e.g., a kernel-level memory scanner) is not meaningfully blocked by `mlock`'s actual guarantee, which is specifically "don't let the OS swap this page to disk" — it says nothing about preventing a co-privileged process or the kernel itself from reading the page directly.
- **The 3A finding (verifier-as-encryption-key) is, if anything, *less* relevant as a distinguishing factor for this specific attacker** compared to Attacker B, because a root-level attacker already has so many other paths to the same outcome (process memory inspection to catch the derived key or plaintext note content mid-use, Frida-style instrumentation to call `CryptoEngine.decryptProcess` directly with attacker-supplied arguments using the app's own loaded code, etc.) that the specific "extract one Hive value, reuse it directly" shortcut is somewhat moot at this privilege level — Attacker B is actually the more *interesting* case for that specific finding, because it shows the app fails even against a **weaker** attacker than root.
- **What Rocen genuinely can still meaningfully limit even against this attacker:** the network-facing side. Even fully compromised locally, an attacker cannot *retroactively* decrypt already-synced `device_key.json`/note ciphertext sitting in a GitHub repository they don't otherwise have credentials for, purely from local device compromise — they would need to *also* separately obtain valid GitHub credentials (which, admittedly, they likely can, per the token-extraction analysis above, but this is a distinct, separately-achieved step, not an automatic consequence of root access alone).

**Severity/classification:** Per the spec's own instruction not to treat root detection as a complete boundary — this section is intentionally not scored RED/ORANGE/etc. in the same way as a fixable bug, because **"a rooted device is close to fully compromised for most local secrets" is close to an inherent property of the Android security model generally, not a Rocen-specific implementation flaw** to remediate. The one Rocen-specific, actionable takeaway is: fixing 3A (the master-key architecture) would raise the bar even for this attacker in one specific way — it would mean a root-level attacker doing *static* analysis of extracted files (rather than live runtime instrumentation) would face the same "need the actual password" requirement as Attacker B would after the fix, rather than the current free pass.

## Attacker D — Malicious/compromised GitHub account or leaked token

Covered substantially in the prior report as Finding I-1; restated here per the spec's specific checklist, with more precision:

| Capability | Can Attacker D do this? | Evidence |
|---|---|---|
| Read notes | **Only unencrypted ones, in full; encrypted ones only as ciphertext (which, per 3A, is only further decryptable if they *also* have `system_crypto_pin`, which residing on GitHub is not — that value never leaves the local device).** | Confirmed via the storage table in Part 1's security model — `password_state.json` and `device_key.json` never contain `system_crypto_pin`. |
| Replace encrypted notes | **Yes.** | `updateFileWithFastForwardCheck` only verifies the caller supplies the current `expectedParentSha` — it has no concept of "is this write coming from a legitimate device," only "is this write building on the current tip." An attacker with valid write-scoped token credentials can read the current SHA (same API Rocen itself uses) and submit any replacement content that passes that single check. |
| Delete notes | **Yes**, via the same `amendSync`/delete-files path Rocen's own legitimate delete flow uses — nothing distinguishes an attacker's delete request from the app's own. |
| Roll back notes to an older version | **Yes — and this is the more interesting, distinct finding, covered fully under Section 11 in Part 3, but flagged here as directly relevant to this attacker.** Because AES-GCM's authentication tag only proves "this ciphertext+tag pair is internally self-consistent and was produced by someone holding the key" — it says **nothing** about *recency*. An attacker with write access can take an old, previously-valid commit's version of an encrypted note's JSON file (trivially available via `git log`/GitHub's own file-history UI, since Git history is not something Rocen's code ever purges) and force-push/recommit it as the current version. Rocen's own fast-forward check (`expectedParentSha`) does not protect against this, because the attacker is *building on the current tip* when they do this — they're not trying to write to a stale parent, they're deliberately writing *new* content (which happens to be a copy of *old* plaintext-once-decrypted content) as if it were fresh. |
| Inject malicious backup records | **Partially — see Attacker F below for the specific "what can malformed/oversized/malicious *content* actually do" analysis; the *access* to inject is unambiguously yes for this attacker.** |
| Cause corruption | **Yes**, by writing structurally-invalid JSON or violating the format invariants `_decodeDevices`/`_buildStateJson` expect — see Attacker F for whether this crashes the app or fails gracefully. |
| Cause a downgrade/restore attack | **Yes, functionally identical to the rollback case above** — "downgrade" and "rollback" collapse into the same mechanism here, since there is no separate "version negotiation" concept distinct from "whatever's the latest commit." |

**Severity: this restates and sharpens Finding I-1 from the prior report as RED**, not merely "high, design-level" as previously softened — per this pass's more careful reading, the *rollback/replay* capability specifically (not just the "impersonate a device for coordination" framing from before) is a concrete, currently-unmitigated integrity gap that a leaked token turns into a real, exploitable attack, not just a theoretical design ceiling. Full remediation detail (monotonic version binding, anti-replay) is deferred to Section 11 in Part 3 to avoid duplicating the fix discussion across two parts.

## Attacker E — Network attacker (intercept/manipulate/delay/replay/redirect)

| Check | Finding | Confidence |
|---|---|---|
| TLS validation | Delegated entirely to `SecureClient` (`smart_dev_pinning_plugin`'s native implementation) — the Dart layer never independently re-validates the certificate chain itself. | Native plugin source not available — **not independently confirmed**, only confirmed that Rocen's own Dart code correctly delegates rather than attempting (and potentially botching) its own TLS validation, which is itself the correct architectural choice. |
| Certificate/public-key pinning | **Genuine SPKI pinning, confirmed correctly implemented at the Dart contract level.** `_validateSpkiPin` checks the pin decodes to exactly 32 bytes (correct length for a SHA-256 SPKI hash) before ever being used, catching a misconfigured pin at app-start rather than at request time (`_validatePinConfiguration` is called both in `_createClient` and lazily in the `_pins` getter). | Confirmed at the Dart layer; native enforcement not independently verified (same caveat as above). |
| Backup pin | Present in the code (`_backupSpkiPin`), but **defaults to an empty string** and is not populated in the reviewed build configuration. | Confirmed — see Part 1's prior-report Finding H-3, restated here as directly relevant to this attacker: **a GitHub key rotation would currently hard-fail all connectivity for every user simultaneously**, with fail-*closed* behavior (see next row) meaning no silent downgrade to insecurity — a good property — but a real availability cliff. |
| Fail-open vs. fail-closed | **Fail-closed, confirmed.** | `_PinnedGithubClient.send()` throws `http.ClientException` unconditionally whenever `response.statusCode == null` (line 178-198) or the native call throws for any reason (the broad `catch (Object e, ...)` at line 155-164 also always rethrows as a `ClientException`, never silently returns a "probably fine" response). There is no code path in the reviewed file that proceeds with a request after a pinning failure. |
| Behavior when pin is outdated | Same as the backup-pin row — hard failure, no automatic recovery, requires an app update. |
| Malicious proxy usable? | **No, if the native pinning implementation genuinely validates the presented certificate's public key against the pin before completing the TLS handshake** (the standard, correct way to implement SPKI pinning) — but this specific guarantee lives entirely in the native plugin, which is unverified. **Filed as: "Not confirmed; requires additional evidence — the native `smart_dev_pinning_plugin` implementation was not available for this review."** |
| Applied to every GitHub request? | **Yes, confirmed for every request that goes through `GithubBackupService`.** | Every method in `github_backup_service.dart` that makes an HTTP call does so via a single shared client field (need to confirm this is literally `CertPinning.client` and not a bypassable alternate — checked: yes, confirmed by the class holding one `http.Client` reference obtained from `CertPinning.client` at construction, with no alternate unpinned `http.Client()` instantiated anywhere else in the file). |
| Any code path bypasses the pinned client? | **None found in `github_backup_service.dart` itself.** Checked the rest of the reviewed codebase for any stray `http.get`/`http.post`/raw `HttpClient()` usage outside this one service class — **none found** in `quicknote.dart`, `clipboard.dart`, `settings.dart`, `bookmarks.dart`, or `ideainbox.dart`. `url_launcher` (present in `pubspec.yaml`) opens URLs in an external browser/app, which is architecturally outside Rocen's own network stack entirely — not a bypass of Rocen's pinning, since Rocen's pinning was never meant to apply to a system browser tab. |
| Redirects | **Not confirmed — genuine gap, flagged precisely.** `_validateUri` validates only the outgoing `request.url` at the top of `send()`; there is no code that re-validates a `Location:` header's target host if the native `SecureClient.httpRequest` call itself internally follows a redirect before returning to Dart. Whether this is exploitable depends entirely on whether the native plugin auto-follows redirects (in which case a compromised/malicious intermediary that issues a 3xx to a different host, if the plugin blindly follows it, would bypass both the host-allowlist check and potentially the pin, since a *new* TLS handshake to a *different* host would need its own pin validation that this code never re-triggers) or does not (in which case the 3xx simply gets returned to Dart as an ordinary non-2xx response with no automatic following, and the risk doesn't materialize). **Filed as: "Not confirmed; requires additional evidence — the native plugin's redirect-following behavior."** |
| DNS-related assumptions | SPKI pinning is inherently DNS-independent (it validates the presented key, not the resolved IP or hostname trust chain beyond the initial hostname match in `_validateUri`) — this is a strength, not a gap; DNS spoofing alone, without also possessing/forging a certificate matching the pinned key, does not defeat this scheme. |
| Proxy behavior | The `forbidden` header list in `_validateHeaders` (`host`, `content-length`, `transfer-encoding`, `connection`, `upgrade`) prevents Rocen's own calling code from manually setting headers that could interfere with the native client's own connection handling — this is a reasonable defensive measure against Rocen's own code accidentally creating ambiguous requests, though it says nothing about a *network-level* proxy's own behavior, which is outside Rocen's code to control at all (this is expected and correct — an app cannot control what a machine-in-the-middle proxy does at the TCP/TLS level below where its own pinning check operates; pinning's entire purpose is to detect and reject exactly that scenario, which the fail-closed behavior above confirms it does). |
| Alternate endpoints | `_validateUri` hardcodes `githubApiHost = 'api.github.com'` and `githubApiPort = 443` — no other host is ever a valid destination for this client, confirmed by the unconditional `throw` if `validHost`/`validPort` fail. |
| Can the auth token leave the intended host? | **No code path found that sends the `Authorization` header to any host other than `api.github.com`.** `_headers`/token usage is entirely internal to `GithubBackupService`, and every request goes through `_validateUri`'s host check before the token-bearing headers are ever attached (the header-attachment and URI-validation happen in the same `send()` call, with `_validateUri` running first and throwing before the request is ever actually dispatched to the native client). |

**Severity: GREEN for everything confirmed at the Dart layer** — this is a genuinely well-built client wrapper. **YELLOW for the two explicitly "not confirmed" items** (redirect-following behavior, and the native plugin's actual TLS/pin-enforcement correctness) — not because there's evidence of a problem, but because the spec's own rules require flagging unverified trust boundaries rather than assuming them safe.

## Attacker F — Malicious repository contents (repository is writable by an attacker)

| Check | Finding |
|---|---|
| Malformed JSON | `jsonDecode` calls throughout `github_backup_service.dart` and `password_state_manager.dart` are consistently wrapped in `try/catch` at their call sites (confirmed pattern: `checkState`'s outer `try { ... } catch (_) { return PasswordStateResult(comparison: checkFailed); }`, and `initializeOrJoinState`'s explicit `FormatException` throws for missing/invalid fields) — **the app fails safely (with a typed exception or a `checkFailed`-style result) rather than crashing on malformed JSON**, for the specific files this was checked against. |
| Unexpected/missing fields | `PasswordStateDevice.fromJson` explicitly validates `deviceNumber`, `deviceId`, `passwordGeneration` are present and well-typed, throwing a descriptive `FormatException` rather than proceeding with null/default values that could silently corrupt device-registry logic — **this is correctly defensive.** |
| Duplicate IDs | `_decodeDevices` explicitly checks for duplicate `deviceNumber` and duplicate `deviceId` using `Set.add`'s return value, throwing `FormatException` on either — **explicitly and correctly guarded**, directly matching what the spec asked to verify. |
| Oversized payloads | **Confirmed gap.** No size check exists before `jsonDecode(res.body)` anywhere in the reviewed files — the full response body is buffered in memory (confirmed via the `StreamedResponse`/byte-array construction pattern in `cert_pinning.dart`) with no upper bound, and then parsed. A malicious repository owner (or an attacker with write access per Attacker D) could commit a very large `password_state.json` or note JSON file; on next sync, Rocen would attempt to fully download and parse it, creating a real (if unsophisticated) memory-exhaustion / crash vector. This is filed as **ORANGE — a genuine, unmitigated availability issue triggerable by repository content the app doesn't control**, not a confidentiality/integrity break. |
| Path traversal via filenames | `listNoteFiles`/`fetchNoteFile` operate on filenames returned by GitHub's own Contents API listing (not raw attacker-supplied path strings interpolated without validation into a local filesystem write) — for the *remote* side, path traversal isn't directly applicable the way it would be for local file writes. The only place local files are actually written based on remote-influenced names is **not found** in the reviewed code — Clipboard's crop-save (this session's earlier work) always constructs its own timestamp-based filename, never derived from remote/GitHub data. **No path-traversal vector found from malicious repository content into local file writes.** |
| Null bytes / unexpected Unicode in fields | Not explicitly tested/sanitized anywhere in the reviewed code (e.g., a `deviceId` or note title containing null bytes or unusual Unicode is not rejected by any validation found) — this is not confirmed to be exploitable (Dart strings handle arbitrary Unicode/embedded nulls without the classic C-string truncation vulnerability class), but it is also not actively defended against, so it's filed as **BLUE — worth adding explicit validation as defense-in-depth, not a confirmed vulnerability**, since I found no concrete way this leads to a security-relevant outcome given Dart's string handling. |
| Resource exhaustion via repeated/nested structures | `_decodeDevices` iterates a flat list with no recursion — no deeply-nested-JSON amplification vector was found in the specific parsing code reviewed (this doesn't rule out a vulnerability inside Dart's own `jsonDecode` implementation itself, which is outside Rocen's code to control and is a widely-used, heavily-tested standard library function). |

**Overall Attacker F severity: the app is genuinely well-defended against structurally-malicious *content* (missing fields, duplicates, wrong types) — GREEN for that category — but has a real, unaddressed ORANGE-level gap for sheer payload size.**

## Attacker G — Malicious/spoofed update or release

**Can users reliably verify an APK came from the legitimate developer and matches the published source?**

**No — and this is directly connected to Finding H-4 from the prior report, restated here in the specific "supply chain" framing the spec requests.**

- The release build is signed with the **debug keystore** (`build.gradle.kts`, `signingConfig = signingConfigs.getByName("debug")`) — the debug keystore's private key is a well-known, publicly-documented default (`~/.android/debug.keystore`, password `android`), meaning **anyone can produce an APK that carries the identical signing certificate fingerprint as Rocen's own "release" build**, defeating Android's entire signature-based update-authenticity model for this app in its current configuration.
- No `proguard-rules.pro` exists, and per Part 1's prior-report Finding H-5, the actual applied ProGuard/R8 configuration is default-only — this doesn't itself relate to authenticity, but compounds the supply-chain concern: a build this loosely pinned down (missing files silently tolerated, debug signing in the release block) suggests the release pipeline itself has not yet been hardened for real distribution, which is exactly the moment to also add the missing authenticity mechanisms below.
- **No evidence of a documented release process was found** in any reviewed file — no `CHANGELOG.md` entry (reviewed separately, this session) references a git commit hash, tag, or APK checksum; no `SECURITY.md` or release-signing-fingerprint documentation was supplied or found referenced.

**Recommendation, directly per the spec's own list:** every public release should publish version, exact git commit/tag, APK SHA-256, and signing certificate fingerprint (obtainable via `keytool -printcert` or `apksigner verify --print-certs`) somewhere users can check independently of the download channel itself (e.g., in the GitHub release notes, signed separately if possible). **This is not proof against a fully-compromised distribution channel, but it is the minimum baseline that lets a user detect a tampered APK if they choose to check** — currently, per this review, there is no mechanism to do so at all.

**Severity: RED**, specifically because it's a **release blocker** per the spec's own definition (a realistic attack — here, "install a lookalike APK signed with the public debug key, distributed through any channel other than an official app store with its own signature-continuity enforcement" — can compromise the integrity of what the user believes is the legitimate app) and it compounds directly with **every other finding in this audit**: if Attacker G can get a user to install a tampered build, none of the cryptographic protections analyzed in Part 1 matter at all, since the tampered build can simply skip or subvert them.
